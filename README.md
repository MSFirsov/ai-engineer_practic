# RAG с нуля

Система вопросов и ответов по документам, написанная без RAG-фреймворков: OpenAI-совместимый клиент, NumPy и Chroma. Цель — разобраться, как устроен RAG (Retrieval-Augmented Generation) изнутри, и улучшать его шаг за шагом.

Учебные документы: `handbook.txt` — справочник сотрудника вымышленной компании «Тундра Лабс», `office.txt` — дополнительные правила офиса. По умолчанию чат работает со справочником. Через Python-функции можно индексировать и искать по нескольким TXT, PDF и DOCX.

## Как это работает

```
ПОДГОТОВКА ДАННЫХ                           ЗАПРОС

handbook.txt                                 вопрос
    │ нарезка окнами по 2 предложения          │ эмбеддинг
    ▼                                          ▼
 куски с заголовком раздела                 вектор вопроса
    │ эмбеддинги                               │ косинусная близость
    ▼                                          ▼
 матрица векторов  ─────────────────────▶  top-k кусков
                                               │ промпт: «отвечай только по контексту»
                                               ▼
                                            LLM → ответ
```

1. Каждый абзац документа режется на предложения, и соседние предложения склеиваются по два. К каждому куску приписывается заголовок его раздела, чтобы кусок был понятен без соседей. Почему выбрана такая нарезка, описано в разделе «Нарезка».
2. Векторы кусков загружаются из дискового кэша; недостающие вычисляются embedding-моделью. В обычном режиме индекс готовится при запуске, в режиме Chroma используется заранее сохранённая коллекция.
3. Вопрос тоже превращается в вектор, и по косинусной близости находятся самые похожие куски.
4. Найденные куски вставляются в промпт с требованием отвечать по контексту и говорить «В документе этого нет», если ответа нет. Соблюдение этого правила зависит от модели и проверяется отдельно.

Чат помнит последние три пары «вопрос — ответ». Перед поиском уточняющий вопрос переписывается в самостоятельный, подробности в разделе «Уточняющие вопросы».

## Запуск

Нужны [uv](https://docs.astral.sh/uv/) и любой сервер с OpenAI-совместимым API. Я использую [LM Studio](https://lmstudio.ai/) с двумя моделями:

- `google/gemma-4-e4b` — чат-модель;
- `text-embedding-bge-m3` — модель эмбеддингов.

Для чата в LM Studio нужно загрузить обе модели и запустить локальный сервер (вкладка Developer → Start Server). Для поиска без генерации и быстрых проверок достаточно embedding-модели.

```bash
uv sync
cp .env.example .env
uv run rag.py
```

## Оценка качества

```bash
uv run evaluate.py
```

`evaluate.py` проверяет систему на наборе вопросов с заранее известными ответами:

- **поиск**: для каждого вопроса известна фраза, которая должна быть в нужном куске. Считаются hit@k (доля вопросов, где нужный кусок попал в top-k) и MRR (насколько высоко он стоит);
- **отказы**: на вопросы, ответа на которые в документе нет, модель должна ответить «В документе этого нет».

Проверенные метрики поиска на 20 вопросах:

| k | hit@k | MRR |
|---|---|---|
| 1 | 0.85 | 0.85 |
| 3 | 0.95 | 0.89 |
| 5 | 1.00 | 0.90 |

В предыдущем эксперименте с генерацией получено 7 отказов из 7; при проверке урока 9 полный набор отказов повторно не запускался. Единственный промах поиска по смыслу при k=3 — «Сколько людей в компании?»: число сотрудников упомянуто одной фразой рядом с рассказом о продукте. Гибридный поиск находит этот кусок, но ухудшает результаты на других вопросах — подробнее ниже.

## Нарезка

`evaluate.py` сравнивает несколько стратегий нарезки на одном и том же наборе вопросов:

| Нарезка | Кусков | Ср. длина, симв. | hit@1 | hit@3 | MRR |
|---|---|---|---|---|---|
| абзацы | 33 | 177 | 0.80 | 0.95 | 0.87 |
| предложения | 65 | 100 | 0.85 | 0.90 | 0.88 |
| **окно 2 предложения** | 42 | 143 | 0.85 | 0.95 | 0.89 |
| окно 3 предложения | 35 | 168 | 0.80 | 0.95 | 0.87 |
| разделы | 13 | 415 | 0.80 | 1.00 | 0.88 |
| окно 2 с перекрытием (шаг 1) | 65 | 137 | 0.95 | 0.95 | 0.95 |

Выводы:

- **Предложения** точнее находятся по конкретному вопросу, но теряют контекст: кусок «Это дни, когда...» непонятен без соседнего предложения.
- **Разделы** дают hit@3 = 1.00 только за счёт размера: три куска — это почти четверть документа. Поиск становится размытым, а в промпт попадает много лишнего.
- **Окно из 2 предложений** выбрано по умолчанию как компромисс между точностью и контекстом.
- **Перекрытие** дало лучшие цифры, но каждое предложение лежит в индексе дважды. Соседние окна почти совпадают и могут занять весь top-k, вытеснив другие нужные куски. Пока оно оставлено как эксперимент.

## Кэш эмбеддингов

Эмбеддинг одного и того же текста одной и той же моделью всегда одинаковый, поэтому векторы кусков сохраняются на диск в `.cache/embeddings/`: один файл `.npy` на кусок. Имя файла — `sha256` от названия модели и текста куска, поэтому:

- после правки документа пересчитываются только изменённые куски;
- одинаковые куски из разных нарезок считаются один раз;
- после смены модели векторы считаются заново, а не берутся от старой модели.

Векторы вопросов кэшируются только в памяти (`lru_cache`): вопросы почти не повторяются между запусками, и на диске копился бы мусор.

В `.cache/embeddings/` хранится кэш векторов, а в `.cache/chroma/` — база Chroma. После удаления кэша векторы будут вычислены заново при подготовке данных. После удаления базы нужно повторно выполнить `--index` для справочника или `sync_document()` для нескольких документов: запуск чата с `--chroma` сам базу не заполняет.

## Уточняющие вопросы

В диалоге люди спрашивают коротко: после «Сколько компания компенсирует на обучение?» идёт «А на спорт?». В таком вопросе нет слов, по которым можно найти нужный кусок. Передать историю диалога модели недостаточно: её увидит только генератор, а поиск по-прежнему получит одну короткую строку.

Поэтому перед поиском модель переписывает вопрос с учётом истории: «А на спорт?» → «Какая компенсация предоставляется на спорт?». Поиск идёт по переписанному вопросу, а в промпт попадает исходный.

`evaluate.py` сравнивает три подхода на 14 уточняющих вопросах:

| Подход | hit@1 | hit@3 | MRR | Время на 14 вопросов |
|---|---|---|---|---|
| как есть | 0.71 | 0.86 | 0.79 | 0 с |
| склейка с предыдущим вопросом | 0.64 | 1.00 | 0.80 | 0 с |
| **переписывание моделью** | 0.93 | 1.00 | 0.96 | 200 с |

Выводы:

- **Как есть** промахивается на вопросах без ключевых слов: «А полностью?», «А кто его согласует?».
- **Склейка** возвращает потерянные слова, но вместе с ними и старую тему. Если пользователь сменил тему («отпуск» → «А в офисе есть кот?»), старый вопрос только мешает, поэтому hit@1 ниже, чем без склейки.
- **Переписывание** даёт лучшие цифры, но стоит около 14 секунд на вопрос. Почти всё это время локальная модель тратит на скрытые рассуждения (300–500 токенов ради ответа из 10). В настоящем проекте для этой задачи подошла бы маленькая быстрая модель без рассуждений.
- Модель иногда искажает вопрос: «Во сколько стендап?» превратилось в «Сколько стоит стендап?». Поиск всё равно нашёл нужный кусок по слову «стендап», так что часть хорошей метрики — везение.
- Длина истории важна: с одной парой «А их можно перенести?» после разговора о больничном переписывается про больничный лист, с тремя — правильно, про дни здоровья.

## Источники ответа

Под каждым ответом чат показывает разделы справочника, из которых взяты найденные куски:

```
Вопрос: Можно ли поработать месяц из Турции?
Ответ: Да, работать из-за границы разрешено не более 30 календарных дней в году.
Источник: 3. УДАЛЁННАЯ РАБОТА; 6. ИСПЫТАТЕЛЬНЫЙ СРОК И АДАПТАЦИЯ
```

Название раздела берётся из первой строки куска. Если модель ответила «В документе этого нет», источники не показываются: поиск всегда что-то возвращает, и ссылки рядом с отказом вводили бы в заблуждение.

На 20 вопросах из набора правильный раздел стоит первым в 18 случаях и есть среди источников во всех 20. В среднем показывается 2,25 раздела, то есть часть из них лишняя: чат показывает всё, что нашёл поиск, а не то, чем воспользовалась модель.

## Гибридный поиск

К поиску по смыслу добавлен поиск по совпадению слов (BM25). Он помогает находить точные строки: время, фамилии, названия каналов и ботов. Перед поиском слова приводятся к нижнему регистру, а стоп-слова удаляются.

Гибрид объединяет до 10 кандидатов от каждого поиска через RRF: за каждое появление в списке кусок получает `1 / (60 + место)`. Баллы складываются, и в контекст попадают три лучших куска.

Запуск гибридного режима:

```bash
uv run rag.py --hybrid
```

Сравнение через `uv run evaluate.py --fast`:

| Набор | Поиск | hit@1 | hit@3 | MRR |
|---|---|---|---|---|
| Обычные вопросы (20) | по смыслу | 0.85 | 0.95 | 0.89 |
| Обычные вопросы (20) | по словам | 0.50 | 0.60 | 0.55 |
| Обычные вопросы (20) | гибрид | 0.65 | 0.95 | 0.78 |
| Точные запросы (14) | по смыслу | 0.71 | 1.00 | 0.85 |
| Точные запросы (14) | по словам | 0.86 | 0.93 | 0.89 |
| Точные запросы (14) | гибрид | 0.86 | 1.00 | 0.93 |

На точных запросах гибрид чаще ставит нужный кусок первым. На обычных вопросах порядок ухудшается: поиск по словам не учитывает синонимы и формы слов, а случайные совпадения могут поднять лишние куски. Поэтому по умолчанию остаётся поиск по смыслу, гибрид включается флагом.

Проверка в чате: с `--hybrid` на вопрос «Сколько людей в компании?» получен ответ «В компании работает 47 человек».

## Chroma: сохранённый индекс справочника

Chroma хранит тексты и готовые векторы в `.cache/chroma/`. Используется локальный `PersistentClient`, отдельный сервер базы не нужен. Векторы документов и запросов вычисляет настроенная embedding-модель.

```bash
uv run rag.py --index
uv run rag.py --chroma --search-only
uv run rag.py --chroma
```

- `--index` сохраняет справочник и завершает работу. Повторная запись неизменённых кусков не создаёт дубликаты.
- `--chroma --search-only` показывает найденные тексты без генерации и истории диалога.
- `--chroma` запускает чат по сохранённой базе без повторного `build_index()`.

Для нового вопроса всё равно нужен его эмбеддинг. `--chroma` и `--hybrid` одновременно не поддерживаются; `--index` запускается отдельно. Обычный `uv run rag.py` сохраняет прежний поиск NumPy.

Проверки без чат-модели:

```bash
uv run evaluate.py --fast
uv run evaluate.py --chroma
```

Первая команда проверяет прежние способы поиска и нарезки. Вторая сравнивает NumPy с сохранённой коллекцией справочника, предварительно проверяя совпадение идентификаторов кусков. Базу она не изменяет.

На текущем справочнике NumPy и Chroma дали одинаковые результаты:

| Набор | hit@1 | hit@3 | MRR при k=3 |
|---|---|---|---|
| Обычные вопросы (20) | 0.85 | 0.95 | 0.89 |
| Точные запросы (14) | 0.71 | 1.00 | 0.85 |

## Несколько документов и обновление источников

Для записей с метаданными используется отдельная коллекция `documents-…`. Коллекция `handbook-…` остаётся для CLI-команд выше. Обе находятся в одной папке базы, но автоматически друг с другом не синхронизируются.

Загрузка документов из корня проекта:

```bash
uv run python - <<'PYTHON'
from pathlib import Path
from rag import HANDBOOK, sync_document, get_documents_collection

print(sync_document(HANDBOOK, "handbook.txt"))
print(sync_document(Path("office.txt"), "office.txt"))
print(get_documents_collection().count())
PYTHON
```

Для учебных файлов ожидаются 42 куска справочника, 3 куска офисных правил и 45 записей всего. У каждой записи сохраняются `source` и `section`. Имя источника задаётся явно; при обновлении нужно использовать то же имя.

`sync_document()` сохраняет актуальные куски и удаляет исчезнувшие только у указанного источника. Идентификатор учитывает источник и текст, поэтому одинаковые тексты разных документов хранятся как отдельные записи. Векторы одинакового текста берутся из общего кэша.

Поиск по всем документам или одному источнику:

```bash
uv run python - <<'PYTHON'
from rag import search_documents

found = search_documents(
    "Как забронировать переговорную Ладога?",
    k=1,
    source="office.txt",
)
print(found[0][1])
PYTHON
```

Результат содержит заголовок `[office.txt / ПЕРЕГОВОРНЫЕ]` и текст про календарь Rooms. Если не передать `source`, поиск выполняется по всей коллекции. Неизвестный источник возвращает пустой список.

Для ответа через чат-модель используется существующая `ask()`:

```python
from functools import partial
import numpy as np
from rag import ask, documents_searcher

answer, found = ask(
    "Как забронировать переговорную Ладога?",
    [], np.empty((0, 0)),
    searcher=partial(documents_searcher, source="office.txt"),
)
print(answer)
```

`partial` закрепляет фильтр для функции, которую затем вызовет `ask()`. Для прямого вызова `search_documents()` он не требуется. CLI-флага для коллекции нескольких документов пока нет: `--chroma` продолжает использовать только коллекцию справочника.

Проверены повторная загрузка, фильтрация, обновление и очистка одного источника без изменения другого, поиск после перезапуска, сохранность записей при ошибке чтения файла или получения эмбеддингов. На трёх проверочных вопросах об офисе получены hit@1 = 1.00 и MRR = 1.00. С фильтром по `handbook.txt` метрики совпали с NumPy из таблицы выше.

Пустой текстовый файл удаляет записи своего источника. Когда нужно обновить источник в базе, запусти `sync_document()` явно. Запись новых и удаление старых кусков выполняются отдельно, поэтому при прерывании синхронизацию нужно повторить. Команда `--index` дописывает записи справочника через `save_to_chroma()`. Обновление с удалением устаревших кусков доступно в `sync_document()` для коллекции `documents-…`.

### Индексация PDF с номерами страниц

Установи зависимости проекта командой `uv sync --locked`. В их числе `pypdf`, который читает текстовый слой PDF. Для индексации и поиска запусти сервер LM Studio с embedding-моделью.

Положи PDF с текстовым слоем в корень проекта и подставь его имя в пример:

```bash
uv run --env-file .env.example python - <<'PY'
from pathlib import Path

from rag import search_documents, sync_document

path = Path("rules.pdf")
print("Кусков:", sync_document(path, source=path.name))
for _, fragment in search_documents("Как забронировать переговорную?", source=path.name):
    print(fragment)
PY
```

Текст каждой страницы нарезается отдельно. В результатах у фрагмента PDF будет заголовок вида `[rules.pdf / стр. 3]`. Одинаковый фрагмент на двух страницах сохраняется как две записи с разными номерами страниц.

Для обновления PDF повтори `sync_document()` с тем же значением `source`. Если файл зашифрован или в нём нет извлекаемого текста, синхронизация завершится ошибкой до изменения записей источника. Сканам без текстового слоя сначала нужно распознавание текста.

### Индексация DOCX с названиями разделов

Библиотека `python-docx` входит в зависимости проекта и ставится через `uv sync --locked`. Чтобы проиндексировать Word-документ, в примере выше замени `Path("rules.pdf")` на путь к своему `.docx`. Для обновления используй то же значение `source`.

Обрабатываются абзацы основного текста. Название раздела берётся из ближайшего заголовка со стилем Word «Заголовок 1», «Заголовок 2» и так далее. В выдаче получится, например, `[rules.docx / Гостевые пропуска]`. Для таблиц и изображений нужно отдельное извлечение. Если в документе нет абзацев основного текста, синхронизация завершится ошибкой и сохранит прежние записи источника.

## Реранкинг через CrossEncoder

Поиск по эмбеддингам отбирает 20 фрагментов справочника. Затем CrossEncoder получает исходный текст вопроса вместе с каждым фрагментом и выставляет паре оценку релевантности. По этим оценкам фрагменты сортируются заново, и берутся три лучших.

Реранкер работает на CPU внутри процесса Python через `sentence-transformers`. Для оценки пар достаточно вызова `model.predict(pairs)`. Через API LM Studio получаем эмбеддинги и запускаем генерацию в чате. [Карточка модели `cross-encoder/mmarco-mMiniLMv2-L12-H384-v1`](https://huggingface.co/cross-encoder/mmarco-mMiniLMv2-L12-H384-v1).

### Установка реранкера

Из корня проекта установи Python-зависимости, включая `sentence-transformers` из `uv.lock`:

```bash
uv sync --locked
```

Затем загрузи модель отдельной командой. LM Studio на этом шаге можно оставить выключенной.

```bash
uv run --env-file .env.example python -c 'from rag import get_reranker; get_reranker(); print("Реранкер готов")'
```

`get_reranker()` передаёт имя модели в `CrossEncoder` и задаёт путь через `cache_folder`. Если кэш пуст, библиотека скачивает веса и файлы токенизатора с Hugging Face в `.cache/reranker/`. Для первого скачивания нужен интернет. Когда появится строка `Реранкер готов`, модель загружена. При следующих запусках веса берутся из кэша. Папка кэша игнорируется Git.

### Проверка поиска

Для сравнения поиска до и после переоценки запусти сервер LM Studio с embedding-моделью:

```bash
uv run evaluate.py --rerank
```

Проверка работает с поиском NumPy и обходится без чат-модели. Для каждого вопроса сравниваются первые три фрагмента до и после переоценки одних и тех же 20 кандидатов. Правильный фрагмент попал в список кандидатов для всех 34 вопросов.

| Набор | hit@1 до → после | hit@3 до → после | MRR до → после |
|---|---|---|---|
| Обычные вопросы (20) | 0.85 → 0.85 | 0.95 → 0.95 | 0.89 → 0.90 |
| Точные запросы (14) | 0.71 → 0.71 | 1.00 → 1.00 | 0.85 → 0.85 |

В этом запуске реранкинг добавил 2,86 с на 34 вопроса без учёта загрузки модели. В чат реранкер можно подключить из Python через `ask(..., searcher=reranked_search)`. Обычный запуск чата использует поиск по эмбеддингам.

## Структурированный ответ и вызов поиска

Pydantic входит в зависимости проекта и устанавливается через `uv sync --locked`. Для примера ниже запусти embedding-модель и чат-модель в LM Studio.

- `generate_structured_answer(question, found)` принимает вопрос и уже найденные фрагменты. Чат-модель возвращает ответ по JSON Schema, а Python получает объект `StructuredAnswer` с полями `has_answer` и `answer`.
- `ask_with_search_tool(question, chunks, vectors)` сначала передаёт модели описание инструмента `search_handbook`. Python проверяет полученный аргумент `query`, выполняет `search()` и отправляет найденные фрагменты модели с ID вызова. Второй запрос возвращает `StructuredAnswer`. Функция также возвращает найденные фрагменты.

```bash
uv run --env-file .env.example python - <<'PY'
from rag import ask_with_search_tool, build_index, generate_structured_answer, search

question = "Сколько дней отпуска в году?"
chunks, vectors = build_index()
found = search(question, chunks, vectors, k=3)
print(generate_structured_answer(question, found).model_dump_json())

answer, _ = ask_with_search_tool(question, chunks, vectors)
print(answer.model_dump_json())
PY
```

Оба вызова выводят JSON с `"has_answer": true` и текстом про 28 дней отпуска. Формулировка ответа может отличаться. На вопрос без ответа в контексте в проверке получен `"has_answer": false` и текст «В документе этого нет». Схема проверяет поля и типы данных. Соответствие ответа документу проверяется по фрагментам.

Обе функции доступны из Python. Команда `uv run rag.py` запускает обычный чат.

## RAG через LangChain

`rag_langchain.py` использует `OpenAIEmbeddings` для запроса векторов у LM Studio, `InMemoryVectorStore` для поиска и `ChatOpenAI` для генерации. Для сравнения с базовой версией используются те же фрагменты справочника, модели и текст промпта из `build_prompt()`.

Оба чата запускаются отдельно. Нарезка, промпт и настройки моделей находятся в `rag_common.py`, который подключают обе версии.

Установи зависимости из lock-файла и запусти обе модели в LM Studio. Для чата используй ту же конфигурацию `.env`, что и для `rag.py`.

```bash
uv sync --locked
uv run rag_langchain.py
```

Введи вопрос по справочнику, например «Сколько дней отпуска в году?». Чат покажет найденные фрагменты, ответ и разделы справочника. Формулируй каждый вопрос целиком: LangChain-версия обрабатывает их по одному, без истории. Для выхода введи `выход` или `exit`.

Для сравнения двух реализаций запусти:

```bash
uv run --env-file .env.example evaluate.py --langchain
```

Вариант `evaluate.py --langchain --fast` выводит только метрики поиска. Для него достаточно embedding-модели. Индекс LangChain строится в памяти при каждом запуске сравнения.

| Набор | NumPy hit@1 / hit@3 / MRR | LangChain hit@1 / hit@3 / MRR |
|---|---|---|
| Обычные вопросы (20) | 0.85 / 0.95 / 0.89 | 0.85 / 0.95 / 0.89 |
| Точные запросы (14) | 0.71 / 1.00 / 0.85 | 0.71 / 1.00 / 0.85 |

В полном прогоне обе версии также прошли три проверки ответов по ожидаемым подстрокам: 28 дней отпуска, канал `#it-help` и отказ на вопрос о зарплате.

Для этого режима в LM Studio достаточно embedding-модели. Сравнение использует одну нарезку справочника и одни и те же вопросы для NumPy, LangChain и LlamaIndex. Каждый вариант строит свой индекс. `rag_llamaindex.py` создаёт индекс LlamaIndex в памяти из готовых фрагментов.

### Постоянный индекс для TXT

В `rag_llamaindex_ingestion.py` на вход поступает целый TXT-файл. `SentenceSplitter` делает фрагменты, а `IngestionPipeline` получает для них эмбеддинги и сохраняет их в Chroma. При повторной загрузке тот же `source` позволяет найти предыдущую версию документа. Неизменившийся файл пропускается.

- `chroma/` хранит тексты и векторы. Для поиска достаточно открыть эту коллекцию.
- `pipeline/` хранит хеши документов и кэш операций. После успешной загрузки сохраняем эту папку через `pipeline.persist()`, чтобы при следующем запуске можно было продолжить обновление.

Создай временную папку с примером:

```bash
export LLAMAINDEX_DEMO_DIR="$(mktemp -d)"
printf '%s\n' 'Бронь длится 90 минут.' > "$LLAMAINDEX_DEMO_DIR/rules.txt"
```

В том же терминале проиндексируй файл и проверь поиск:

```bash
uv run --env-file .env.example python - <<'PY'
import os
from pathlib import Path

from llama_index.core import VectorStoreIndex

from rag_llamaindex import create_llamaindex_embeddings, search_llamaindex
from rag_llamaindex_ingestion import (
    open_llamaindex_store,
    restore_llamaindex_pipeline,
    sync_llamaindex_document,
)

root = Path(os.environ["LLAMAINDEX_DEMO_DIR"])
state_dir = root / "pipeline"
store = open_llamaindex_store(root / "chroma")
pipeline = restore_llamaindex_pipeline(store, state_dir)
processed = sync_llamaindex_document(root / "rules.txt", "rules.txt", pipeline)
pipeline.persist(persist_dir=str(state_dir))

index = VectorStoreIndex.from_vector_store(store, embed_model=create_llamaindex_embeddings())
found = search_llamaindex("Сколько длится бронь?", index, k=1)
print("Обработано фрагментов:", processed)
print(found[0][1])
PY
```

Первый запуск обработает один фрагмент. Если повторить только второй блок, он покажет `0` обработанных фрагментов, и правило по-прежнему найдётся. Замени в `rules.txt` 90 на 60 и запусти второй блок снова. Выдача покажет новую версию.

## Настройки

Задаются в `.env`:

| Переменная | Назначение | По умолчанию в `.env.example` |
|---|---|---|
